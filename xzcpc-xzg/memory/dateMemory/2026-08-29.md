# 2026-08-29 补发联动企迈出库单 + 换算失败可重试策略 + 启动/编译修复

## 背景

飞书 H5 补发页点「补发」后联动企迈 9.2.4 创建出库单（自动扣库存）。此前 convertQty 的 SQL 写错（列名不存在 + 按 material_id 直查）→ 异常被 catch 吞掉 → **降级按原数量建单** → 7 张出库单数量错 24 倍/16 倍/12 倍/5 倍。本次修复换算 + 废除降级 + 支持失败重试。

## 一、出库单联动（口径定稿，用户两次纠正后强制）

- **数量**：`num` 按**库存单位**（`stock_unit`，回退 `purchase_unit`），报损数量经 `material_conversion_rule` 换算链换算
- **单价**：`price` = **采购单价 `purchase_price`**（material_inventory_rule）
- ❌ 绝不使用 `order_unit`/`order_price`（用户原话：「补发，单位是用库存单位，单价是采购单价！」）
- **接口**：企迈 9.2.4 `POST /v3/scm/order/outbound/order/create`；productList 无单位字段；`autoOutbound=1` 立即扣库存；warehouseNo 用 **PSCK 格式编码**（非控制台数字 ID）
- **幂等**：`externalNo = BF{base}-{seq}`（base=首条 id，seq 按仓库分组序号；失败占位 `BF{id}-0`），`outbound_order.external_no` 唯一键，`insertOutboundOrder` upsert（先 UPDATE 后 INSERT）

### 仓库映射（resolveOutboundWarehouse）

| 条件 | 仓库 |
|------|------|
| 分类=冷冻类 或 名称含 FROZEN_MATERIAL_KEYS（安佳淡奶油/酸奶/咸法干酪乳/牛油果泥） | 冷冻仓 `PSCK000149` |
| 分类=鲜奶类 | 鲜奶仓 `PSCK000070` |

## 二、convertQty 换算（SQL 修复 + 失败语义变更）

- **SQL 修复**：`material_conversion_rule` 表**没有 material_id 列**！必须 `JOIN material_inventory_rule ir ON ir.rule_id = c.rule_id WHERE ir.material_id=?`；列名是 `from_quantity/to_quantity`（不是 from_qty/to_qty）。旧 SQL 每次执行抛 Unknown column → catch 吞掉 → 降级建单
- **换算算法**：`ConversionFactorUtil.computeConversionFactor(fromUnit, toUnit, rules)` 双向 BFS（每条边双向 ratio，仅 unit 类型），如 1包=250g、1件=6000g → 包→件 = 1/24
- **换算失败新语义（本次核心）**：**不再降级按原数量建单**！
  - 单位缺失 / 无换算链 / 换算异常 → `convertQty` 返回 **null**
  - `createOutboundForLoss` 收到 null → `markOutboundFailed(r, wh, "物料缺少换算链（input_unit → stock_unit）…")` + continue（不进建单分组，**绝不带错误数量建单**）
  - `markOutboundFailed`：写 `BF{id}-0` failed 占位（含仓库编码 + error 原因）+ UPDATE loss_report.outbound_order_id + `sendOutboundAlert` 飞书告警（sys_config `loss_outbound_alert_chat_id` 有值只发该群，否则发其他类补发收件人）
- **门店补发不受影响**：`issueVoucher`/`batchIssueVoucher` 里 `status='confirmed_resend'` 的 UPDATE **先于** `createOutboundForLoss` 执行（独立语句）——换算失败只标记出库，本地状态照常流转，小程序收货流程照常
- **重试闭环**：H5 已补发 tab 失败行显示红行（⚠ 出库失败 + error）+ 「重新补发」按钮 → `POST /api/public/loss-report/retry-outbound {id}` → 重新走 createOutboundForLoss：成功 → `BF{id}-1` 新单（upsert 覆盖无冲突）；再失败 → 覆盖 `BF{id}-0` failed 记录 + 再告警
- **H5 判断**：列表接口返回 `outbound_status`（JOIN outbound_order o，o.status AS outbound_status），前端 `outboundStatus === 'failed'` 显示红行 + 重试按钮；tab 切换真实模式 `location.reload()`（localStorage activeTab_<cardKey>），**TEST_MODE（URL test=1）前端模拟不 reload**（testShowDoneTab/testShowPendingTab）

## 四、启动失败修复（部署 server 时踩坑）

新 jar 启动报 `IssueFeedbackServiceImpl constructor parameter 3 ... No qualifying bean of type Executor ... found 3: logTaskExecutor, alertTaskExecutor, taskScheduler`。两个叠加根因：

1. **m2 依赖 jar 落后于工作区**：工作区大量未提交改动（8/28-29），本地 m2 的 common jar 是 8/11 旧版（无 `feedbackNotifyExecutor` bean）。`mvn package -pl server`（不带 -am）引用 m2 旧 jar → 新 jar 里 common 是旧的
   - **修复**：`mvn install -pl common,template,task,expense,people -DskipTests`（排除编译不过的 mp）→ 重新 `mvn package -pl server`
2. **Lombok 构造注入丢 @Qualifier**：`@Qualifier("feedbackNotifyExecutor") private final Executor x;` + `@RequiredArgsConstructor`——Lombok 生成的构造参数**不带字段上的 @Qualifier**，编译又无 `-parameters`（pom 未配）→ Spring 按类型匹配 Executor 命中多个
   - **修复**：改 `@Autowired @Qualifier(...)` **字段注入**（去掉 final，Lombok 构造器不再含该参数；@Qualifier 在字段上生效）
   - 全项目排查：仅 IssueFeedbackServiceImpl 一处（新文件，未提交）

## 五、mp 编译错误（已修复）

- **mp 之前的「找不到符号」**（MpTaskServiceImpl:288/737/738、SmartOrder:124/125/149/150/172/519/2005）：m2 旧 task jar 缺新实体方法（getTaskType 等），install 新 task 后**自动消失**（不是工作区代码问题）
- **唯一真错误**：`SmartOrderServiceImpl.java:372` —— `Task.getId()` 返回 `Integer`（Task.id 是 Integer），`persistOrder(..., Long taskId, ...)` 参数要 Long → 改 `.longValue()`
- 修复后**全量 `mvn clean package -DskipTests` 通过**，server + mp-server 两个 jar 均为全模块最新代码（此前 server jar 的 mp 部分是 8/11 旧 jar）
