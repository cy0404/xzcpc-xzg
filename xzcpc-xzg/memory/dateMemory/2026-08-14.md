### 实现（LossReportH5Controller.java + loss-daily-confirm.html）
- **新接口** `GET /api/public/loss-report/download-videos-plan`：只统计大小 + 打 download 日志（`markDownloaded=1`），返回 `{code, split, parts, base, names, totalSize}`

- **分包文件名**：`物料名-总数量单位-供应商-日期-partNofM.zip`（单包无后缀），分包 ZIP 同样缓存在 `upload/zips/`
- **前端 doDownload**：先 fetch plan 接口（markDownloaded=1），再按 `plan.parts` 每隔 3 秒依次 `<a>` 点击下载 `plan.base + '&part=N'`；plan 失败 alert 提示

## 视频ZIP下载缺文件修复（HTTP兜底双重编码 + 本地读取失败回退）

### 现象（生产日志 15:49）
下载蓝蛙牛油果 ZIP（象子茶铺茶孟定店 8包）时 `3.jpg`、`4.mp4` 两条目打包失败，但接口仍返回 200 → 下载的 ZIP 静默缺文件，页面不报错。

### 根因1：HTTP 兜底 URL 双重编码（日志铁证）
- `rt.execute("http://localhost:30261" + ve.url, ...)`：ve.url 已是编码后的 `%E8%B1%A1...`（中文门店名），RestTemplate 对 String URL 当 URI 模板再编码一次 → 请求行 `%25E8%25B1...`
- mp 端（UploadResourceConfig 静态资源）Tomcat 只解一次码 → 去找字面 `%E8...` 文件名的文件 → 404 → 条目丢失
- `remoteFileSize` 的 HEAD 探测同样双重编码 → 404 按 0 计 → **拆包计划 totalSize 偏低、分包划分失真**（该文件没算进大小）
- 旧代码同样构造，一直存在；以前多数文件本地磁盘命中，兜底少触发，未暴露

### 根因2：拆包重构引入的回归
- 旧代码本地读取包 try/catch，失败继续走 HTTP 兜底；重构后 `buildPartZip` 里 `localFile != null` 但 `Files.copy` 抛异常 → 直接丢条目不再兜底
- 3.jpg 即此情形（无「走HTTP兜底」日志说明本地找到了文件但 copy 失败；旧 WARN 不带异常信息无法确认具体原因）

### 修复（LossReportH5Controller.java）
1. 新增 `httpUrl(path)`：先 `URLDecoder.decode(path, "UTF-8")` 再拼 `http://localhost:30261`（RestTemplate 会自动正确重新编码一次），解码失败兜底原串；`remoteFileSize` 和 `buildPartZip` 的兜底统一走它
2. `buildPartZip` 本地读取改为「putNextEntry 前先开流验证」，copy/开流失败转 HTTP 兜底（`viaHttp` 标志；失败时 putNextEntry 会自动关掉损坏的半截条目，再写同名完整条目，解压工具以后一条为准——对齐旧代码行为）
3. 「下载视频失败」WARN 带上 `e.getMessage()`，下次失败可直接定位原因

### 运维
- server 端需重新打包部署
- **部署后删除 server 的 `upload/zips/` 缓存**：今天失败的 ZIP 已按文件名缓存，不清会一直下到缺文件的旧包（可全清，按需重建）
- 坏 ZIP 已到总部手里的话需重新下载
- 用户清缓存后仍损坏 → 原因：server jar 还没重新部署，旧代码重建了坏包又缓存上；正确顺序=打包部署→清 zips→重新下载

### 建议量算法（获批版）
- **物料池 + 当前库存**：最近一次已提交盘点任务的 `task_material_summary`（⚠️ 计划原写 store_zone_material，实现中发现它是**空表**——全仓库无写入者，grep + git log 验证；store_zone_material 的 material_id 是 material.id BIGINT，而 task_material_summary 的 material_id 是 VARCHAR 外部编码，join 语义不同已分别处理）
- **dailyUse 库存差法**：`(前次盘点库存 + 期间企迈报货单入库 − 本次盘点库存) ÷ 间隔天数`；取最近 2 个已提交任务（LIMIT 2）；入库来源用**报货单列表+明细**（getDeclareOrderList→getDeclareOrderDetail，按 productCode=qm_code 精确匹配，最多 20 条详情；console 入库单 API 商品行无 productCode 不可用）；任何失败 try/catch 兜底 sys_config 默认 0.5/天
- **base** = `max(0, dailyUse×(cycleDays+safetyDays) − current)`；cycleDays/safetyDays 取 sys_config `smart_order_delivery_cycle_days`(7)/`smart_order_safety_days`(3)，**预留企迈源接口**（用户说后续从企迈拉）
- **单位修正**：base 在 base_unit 计算，经 `ConversionFactorUtil.computeConversionFactor(stockUnit, baseUnit, rules)` BFS 双向图换算到 stock_unit；存在 unit 类型换算链 → CEILING 取整（整箱/整包），否则保留 2 位小数
- 只入 suggest>0 且 qm_code 非空的物料；reason 存表（"当前库存约可支撑 X 天，建议补至 Y 天用量" / "暂无盘点数据，按日均消耗估算" + "· 按整箱规格向上取整"）；support_days = current÷dailyUse

### 状态机与确认两阶段
- pending → syncing → success（qmai_declare_no）/ submit_failed（submit_error，可重试）
- **Phase A 短事务**：`LambdaUpdateWrapper` 条件更新 `status IN(pending,submit_failed)`→syncing + confirmed_by/at + sync_attempts+1，rows≠1 报并发冲突；同步写各明细 confirmed_qty；**提交事务**（远程调用绝不持事务）
- **Phase B 无事务**：resolveWarehouseNo → 构建 productList（confirmed_qty>0 的明细）→ createDeclareOrder
- **Phase C 短事务**：落终态（final 副本防 lambda 捕获编译错误）；失败抛 BusinessException 让前端回状态可重试
- **卡死恢复**：status=syncing 且 updated_at 超 5 分钟 → 重置 submit_failed 允许重试
