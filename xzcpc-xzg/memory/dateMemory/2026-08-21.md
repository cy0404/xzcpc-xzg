## Issue 回调状态不更新：乐观锁并发竞态（已修复）

**用户反馈**：issue callback 已到达（日志两条同秒 10:16:13.168），但问题状态没有变化。

**根因（DB 证据实锤）**：`issue` 表带 `@Version` 乐观锁（MyBatis-Plus `OptimisticLockerInnerInterceptor` 生效中）。
- `/callback`（syncByCallback）与 `/callback-records`（saveRecords）两个回调并发到达，同时 `selectById` 读到 `version=0`
- records 先 update 成功（version 0→1）；状态回调 `updateById` 生成 `SET version=version+1 WHERE version=0` → **静默影响 0 行**，不抛异常、无重试、状态不更新
- 查库证实：row 568 `status=PENDING_CONFIRMATION`、`version=1`（version 已被 records 推进，callback 的状态写丢了）

**修复（IssueServiceImpl.java）**：
- 新增 `updateWithRetry(issue)`：`updateById` 影响 0 行时重读最新 version 回填后重试，最多 3 次；`syncByCallback` / `applyExternalStatus` 改走它
- `saveRecords` 改为 `LambdaUpdateWrapper` **只更新 records_data + updated_at**：不更新整个实体 → 不触发乐观锁、不写回旧字段，与状态回调并发时不占 version 位、也不覆盖对方刚写入的状态
- 编译验证：`mvn compile` 通过；待 mp-server 重新打包部署

⚠️ **通用教训**：所有带 `@Version` 的表，并发 select-then-updateById 都可能静默丢更新；写路径要么按需只更新自己的字段（wrapper），要么对 0 行影响重试。

## InboundSyncJob 失败不告警飞书（已修复 + 临时停用）

**用户反馈**：`Table 'store_inventory.inbound_order' doesn't exist` 这种报错没发到飞书群。

**原因**：`FeishuWebhookAlertService` 只从 `GlobalExceptionHandler`（HTTP 请求异常）+ `MpInboundServiceImpl` 收货流程触发；**定时任务里 catch 的异常只 log.error，不会告警**。

**修复（InboundSyncJob.java）**：`syncAll()` 汇总失败——收集 firstError + 最多 5 个失败门店（storeId + 截断 100 字符消息），`fail>0` 时调用 `alertFailure()`：构建 `FeishuAlertContext`（httpMethod="JOB"、requestPath="/job/inbound-sync"、userHint="ok=X fail=Y 失败门店: ..."）→ `feishuAlert.notify(ctx, firstError)`，一条汇总告警替代 168 条刷屏。
